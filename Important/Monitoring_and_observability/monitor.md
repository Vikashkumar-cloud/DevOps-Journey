# Prometheus Notes

## What is Monitoring?

Monitoring is the process of continuously collecting and analyzing information about systems, servers, applications, and networks to ensure they are working properly.

### Why is monitoring needed?

We cannot run every command manually on every server every minute. That’s why we use monitoring tools to collect this information automatically.

### Benefits

- Detect Problems Early
- Reduce Downtime
- Performance Analysis
- Capacity Planning
- Troubleshooting

## What Do We Monitor?

There are four major areas:

### Infrastructure Monitoring

Monitoring servers and operating systems.

Examples:

- CPU usage
- Memory usage
- Disk usage
- Swap usage
- Load average
- Processes
- Network usage

### Application Monitoring

Monitoring application performance.

Examples:

- Request count
- Response time
- Error rate
- Active users

### Networking Monitoring

Monitoring network devices and traffic.

Examples:

- Bandwidth
- Packet loss
- Latency
- Network errors

### Log Monitoring

Monitoring logs generated by applications and systems.

Examples:

- `/var/log/messages`
- `/var/log/syslog`
- `/var/log/nginx/error.log`

# Metrics vs Logs vs Traces

This is one of the most important interview topics.

## Metrics

- Metrics are numerical values collected over time.
- Examples: CPU usage, memory usage, disk usage, HTTP requests.
- Prometheus mainly works with metrics.

## Logs

- Logs are detailed records of events.
- Examples:
  - Database connection failed
  - User login successful

## Traces

- Traces track a request across multiple services.
- Example: `User Request → Frontend → API → Database`
- Tracing shows where time was spent.
- Tools: Jaeger, Zipkin, OpenTelemetry.

| Feature | Metrics | Logs | Traces |
|---|---|---|---|
| Data Type | Numbers | Events | Request Path |
| Example | CPU = 70% | Login Failed | Request Journey |
| Used For | Monitoring | Troubleshooting | Performance Analysis |
| Tool | Prometheus | ELK/Loki | Jaeger |

# Observability

Monitoring tells you:

> “Something is wrong.”

Observability tells you:

> “Why it is wrong.”

Observability consists of three pillars:

- **Metrics:** CPU = 75%
- **Logs:** Application crashed
- **Traces:** Database query took 15 seconds

# Four Golden Signals

These were introduced by Google for monitoring distributed systems.

## Latency

How long a request takes.

Example:

- Login API = 200ms
- If it becomes Login API = 5 seconds, users will notice delays.

## Traffic

How much demand your system is handling.

Examples:

- Requests per second
- Network traffic
- Users connected

## Errors

Failed requests.

Example:

- Total Requests = 1000
- Failed Requests = 100
- Error rate = 10%

## Saturation

How busy your resources are.

Examples:

- CPU = 95%
- Memory = 90%
- Disk = 98%

This indicates the system is close to its limit.

# What is Prometheus?

Prometheus is an open-source monitoring and alerting tool that collects, stores, and analyzes metrics from servers, applications, containers, and Kubernetes clusters.

### In simple words

Prometheus continuously checks the health of your infrastructure by collecting metrics like CPU, memory, disk usage, and application performance.

## Simple Flow of Prometheus

```text
Every 15 seconds
      ↓
Prometheus collects
      ↓
CPU, Memory, Disk, Network, Application Metrics
      ↓
Dashboard
      ↓
Alerts
```

## Why Did Prometheus Become Popular?

Prometheus is especially well-suited for modern DevOps environments because it:

- Automatically discovers services.
- Works very well with Kubernetes.
- Collects metrics without agents (using exporters where needed).
- Has a powerful query language (PromQL).
- Integrates with Grafana.
- Supports alerting.
- Is open source.

# Features of Prometheus

## Time Series Database (TSDB)

Prometheus stores data as time series.

A time series is:

> A metric value associated with a timestamp.

Instead of only storing the current CPU usage, Prometheus stores its history. This allows you to see trends over time.

| Time | CPU Usage |
|---|---:|
| 10:00 | 35% |
| 10:01 | 38% |
| 10:02 | 42% |
| 10:03 | 40% |

## Pull-Based Architecture

Prometheus pulls metrics from targets.

- The server does not send data automatically.
- Prometheus collects it at regular intervals.
- Example: every 15 seconds.

```text
Prometheus
    ↓
http://server:9100/metrics
    ↓
Collect Metrics
```

## PromQL

PromQL lets us query metrics.

Examples:

```promql
up
avg(node_cpu_seconds_total)
topk(5, node_memory_MemTotal_bytes)
```

- `up` → Show all active targets.
- `avg(node_cpu_seconds_total)` → Average CPU.
- `topk(5, node_memory_MemTotal_bytes)` → Top 5 memory-consuming instances.

## Alerting

Prometheus can detect issues such as:

- CPU > 90%
- Memory > 85%

It sends alerts to Alertmanager, which can notify us via:

- Email
- Slack
- Microsoft Teams
- PagerDuty
- Webhooks

## Service Discovery

In cloud environments, servers are constantly created and removed.

Instead of manually updating configurations, Prometheus can automatically discover targets from:

- Kubernetes
- AWS EC2
- Docker
- Consul

## Multi-Dimensional Data Model

Metrics can have labels.

Labels make filtering and grouping much more powerful.

Example:

```text
cpu_usage
```

becomes:

```text
cpu_usage{instance="server1",job="node-exporter",region="mumbai"}
```

# Limitations of Prometheus

## Metrics Only

Prometheus is designed for metrics; it is not a log management tool.

## Limited Long-Term Storage

It stores metrics locally by default.

For long-term retention or multi-cluster setups, many organizations use projects such as:

- Thanos
- Mimir

## Pull Model Limitations

Prometheus primarily uses a pull model, which can be unsuitable for some short-lived jobs.

## No Built-in Dashboards

Grafana is commonly used for visualization.

# Pushgateway

Normally, Prometheus pulls metrics.

Some jobs are very short-lived.

Example:

```text
Backup script
    ↓
Runs for 10 seconds
    ↓
Stops
```

If Prometheus scrapes every 15 seconds, it may miss the metrics because the job has already finished.

### Solution

The short-lived job sends its metrics to Pushgateway.

```text
Backup Script
    ↓
Pushgateway
    ↓
Prometheus
    ↓
TSDB
```

### When to Use Pushgateway

Use it for:

- Batch jobs
- Cron jobs
- One-time scripts

Avoid using it for long-running services like web applications, because Prometheus can scrape those directly.

# Interview Questions — Architecture

### What is the role of the Prometheus Server?

The Prometheus server scrapes metrics from targets, stores them in its Time Series Database (TSDB), executes PromQL queries, evaluates alert rules, and sends alerts to Alertmanager.

### What is a Target in Prometheus?

A target is any endpoint that exposes metrics for Prometheus to scrape, such as a Linux server, Kubernetes Pod, application, or database.

### Why do we need exporters?

Exporters collect metrics from systems or applications and expose them in the Prometheus metrics format. This allows Prometheus to monitor systems it cannot read directly.

### What is TSDB?

TSDB (Time Series Database) is Prometheus’s built-in database that stores metrics along with timestamps, enabling historical analysis and trend visualization.

### What is the difference between Alertmanager and Prometheus?

Prometheus detects conditions that should trigger alerts based on alert rules.

Alertmanager receives those alerts, groups them, suppresses duplicates, manages silences, and sends notifications to channels like email or Slack.

### When should you use Pushgateway?

Pushgateway is used for short-lived batch jobs or Cron jobs that finish before Prometheus has a chance to scrape their metrics.

Long-running services should be scraped directly by Prometheus instead of using Pushgateway.

# Linux Installation

Update packages:

```bash
sudo apt update
```

Download Prometheus from the latest release page and copy the download link.

Extract the archive:

```bash
tar -xvf prometheus-*.tar.gz
```

Inside the extracted directory you’ll find:

```text
prometheus/
├── prometheus
├── promtool
├── prometheus.yml
├── consoles/
└── console_libraries/
```

## Create Prometheus User

For security, don’t run Prometheus as the root user.

```bash
sudo useradd --no-create-home --shell /usr/sbin/nologin prometheus
id prometheus
```

## Create Required Directories

```bash
sudo mkdir /etc/prometheus
sudo mkdir /var/lib/prometheus
```

## Copy Configuration

```bash
sudo cp prometheus.yml /etc/prometheus
```

## Copy Binaries

```bash
sudo cp prometheus /usr/local/bin/
sudo cp promtool /usr/local/bin/
```

## Set Ownership

```bash
sudo chown -R prometheus:prometheus /etc/prometheus
sudo chown -R prometheus:prometheus /var/lib/prometheus
```

## Create the systemd Service

```ini
[Unit]
Description=Prometheus Monitoring
After=network.target

[Service]
User=prometheus
Group=prometheus
ExecStart=/usr/local/bin/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus
Restart=always

[Install]
WantedBy=multi-user.target
```

- `Description` → Service description.
- `After=network.target` → Starts Prometheus after networking is available.
- `User=prometheus` → Runs the service as the Prometheus user.
- `Restart=always` → Automatically restarts Prometheus if it crashes.

Reload systemd:

```bash
sudo systemctl daemon-reload
```

Start Prometheus:

```bash
sudo systemctl start prometheus
```

Access:

```text
http://SERVER-IP:9090
```

Verify configuration:

```bash
promtool check config /etc/prometheus/prometheus.yml
```

# Installation Interview Questions

### Why do we create a separate Prometheus user?

To follow the principle of least privilege. Running Prometheus as a non-root user improves security by limiting the impact of a compromise.

### What is the purpose of prometheus.yml?

It is the main configuration file that defines global settings, scrape jobs, targets, alerting configuration, and rule files.

### Why do we use systemd for Prometheus?

systemd manages the Prometheus process, starts it automatically on boot, restarts it if it fails, and allows administrators to monitor its status using standard Linux service commands.

### What is the difference between installing Prometheus with Helm and using Prometheus Operator?

Helm installs a packaged set of Kubernetes resources.

The Prometheus Operator extends Kubernetes with custom resources and automatically manages Prometheus instances, monitoring configurations, and related components, making it better suited for larger production environments.

A Kubernetes Operator is software that extends Kubernetes using Custom Resource Definitions (CRDs) and a controller.

It continuously watches the cluster and ensures the actual state matches the desired state.

The controller.

- Creates Prometheus Pods

A ServiceMonitor tells Prometheus:

> “Monitor this Kubernetes Service.”

Flow:

```text

```

Without a ServiceMonitor, Prometheus does not know it should scrape that application.

Example:

```yaml

kind: ServiceMonitor
metadata:
  name: nodejs-monitor
spec:
  selector:

  endpoints:
    - port: http

```

Sometimes an application doesn’t have a Service.

```text

```

- Alertmanager Pods
- Services
- Configurations

Instead of editing YAML files inside Prometheus, create:

```yaml

```

The Operator automatically loads it.

No restart is required.

Example:

```yaml
groups:
  - name: cpu
    rules:
      - alert: HighCPU
        expr: cpu_usage > 90
```

# What is a Metric?

A metric is a numerical measurement collected over time.

### In simple words

A metric is a number that tells us how a system or application is performing at a specific point in time.

Examples:

- CPU Usage = 35%
- Memory Usage = 62%
- Disk Usage = 75%
- Network Traffic = 120 MB/s

These numbers describe the “health” of your infrastructure.

## How Prometheus Stores Metrics

Every metric has:

- Metric Name
- Value
- Timestamp
- Labels (optional)

# Prometheus Metric Types

Prometheus provides four metric types:

| Metric Type | Purpose |
|---|---|
| Counter | Counts things that only increase |
| Gauge | Measures values that increase and decrease |
| Histogram | Measures value distribution |
| Summary | Measures distribution and calculates quantiles |

## Counter

A Counter is a metric that only increases.

It can:

- Increase
- Stay the same
- Reset to zero when the application restarts

It never decreases during normal operation.

Examples:

- Total HTTP requests
- Total logins
- Total orders
- Total errors
- Total API calls

Common Counter metrics:

```text
http_requests_total
process_start_total
login_attempts_total
database_queries_total
errors_total
```

### Analogy

Imagine a ticket counter at a cinema:

```text
Person 1 → Tickets sold 1
Person 2 → Tickets sold 2
Person 3 → Tickets sold 3
...
```

Tickets sold never become `3 → 2 → 1` unless the counter is reset.

## Gauge

A Gauge can increase and decrease. It represents the current value.

Examples:

- CPU Usage
- Memory Usage
- Disk Usage
- Temperature
- Active Users
- Queue Length

Prometheus examples:

```text
node_memory_MemAvailable_bytes
node_filesystem_avail_bytes
```

### Analogy

Think about the fuel gauge in a car:

```text
Full → Half → Quarter → Full Again
```

## Histogram

A Histogram measures the distribution of values by grouping them into buckets.

Common uses:

- Request duration
- API latency
- File upload time
- Database query time

### Analogy

Suppose 100 students take an exam. Instead of recording every student’s marks individually, group them:

```text
0-20   → 5 students
21-40  → 12 students
41-60  → 30 students
...
```

These groups are called **buckets**.

### HTTP Response Example

Request times:

```text
0.1 sec
0.3 sec
0.5 sec
1.2 sec
2.5 sec
```

Histogram buckets:

```text
<= 0.1 sec
<= 0.5 sec
<= 1 sec
<= 2 sec
<= 5 sec
```

Prometheus creates three metrics for a histogram such as:

```text
http_request_duration_seconds_bucket
http_request_duration_seconds_sum
http_request_duration_seconds_count
```

## Summary

A Summary also measures distributions, but it calculates quantiles (percentiles) on the application side.

Examples:

- Median response time
- 95th percentile
- 99th percentile

Prometheus example:

```text
http_request_duration_seconds
    ├── 50th percentile
    └── 95th percentile
```

## Histogram vs Summary

| Histogram | Summary |
|---|---|
| Uses buckets | Uses quantiles |
| Quantiles can be calculated later with PromQL | Quantiles are calculated by the application |
| Better for aggregating data across multiple instances | Not suitable for aggregating quantiles across instances |
| Commonly recommended for distributed systems | Good for single-instance measurements |

## Which Metric Type Should We Choose?

| Scenario | Metric Type |
|---|---|
| Total login attempts | Counter |
| Total API requests | Counter |
| CPU usage | Gauge |
| Memory usage | Gauge |
| Disk usage | Gauge |
| Request latency | Histogram |
| Database query duration | Histogram |
| Response time percentiles | Summary (or Histogram + PromQL in many cases) |

### Histogram vs Summary — Interview Question

**Histogram:** Groups observations into configurable buckets and lets Prometheus calculate percentiles later using PromQL. It is suitable for aggregating data from multiple instances.

**Summary:** Calculates percentiles (quantiles) inside the application itself and exposes those values directly. It is useful for single instances but is generally not suitable for aggregating percentiles across multiple instances.

# Exporters in Detail

An Exporter is a small application that collects metrics from a system or application and exposes them in a format that Prometheus understands.

> Exporter = Collector + Translator

It:

1. Collects information from a system.
2. Converts it into Prometheus format.
3. Makes it available at a `/metrics` endpoint.

Prometheus then periodically visits that endpoint and collects (scrapes) the metrics.

## How Does an Exporter Work?

```text
Step 1:
Linux has information like CPU, Memory, Disk, Network.

Step 2:
Node Exporter reads this information.

Step 3:
Node Exporter converts it into Prometheus metrics.

Step 4:
Node Exporter exposes http://server:9100/metrics

Step 5:
Prometheus scrapes every 15 seconds. GET /metrics

Step 6:
Prometheus stores metrics in TSDB and Grafana displays them.
```

# prometheus.yml

Prometheus doesn’t automatically know what to monitor.

We have to tell it:

- Which servers to monitor
- Which applications to monitor
- How to monitor them

All of this is done in:

```text
prometheus.yml
```

## What is prometheus.yml?

It is the main configuration file.

When Prometheus starts, it reads this file to know:

- What to monitor
- How to monitor

# PromQL Functions

## rate()

One of the most used PromQL functions.

It calculates how fast a counter is increasing.

Example:

```promql
rate(http_requests_total[5m])
```

Meaning:

> How many HTTP requests per second occurred over the last 5 minutes?

## increase()

Returns the total increase over a period.

```promql
increase(http_requests_total[1h])
```

Meaning:

> How many requests were received in the last hour?

## sum()

Adds values together.

```promql
sum(node_memory_MemAvailable_bytes)
```

Returns total available memory across all monitored instances.

## avg()

Returns the average.

```promql
avg(node_load1)
```

Returns average system load.

## max()

Returns the highest value.

```promql
max(node_memory_MemAvailable_bytes)
```

Returns highest available memory.

## min()

Returns the lowest value.

```promql
min(node_memory_MemAvailable_bytes)
```

Returns lowest available memory.

## count()

Counts the number of series.

```promql
count(up)
```

Returns how many targets are being monitored.

## topk()

Shows the top N values.

```promql
topk(5, node_memory_MemAvailable_bytes)
```

Shows the 5 servers with the most available memory.

## bottomk()

Shows the lowest N values.

```promql
bottomk(5, node_memory_MemAvailable_bytes)
```

Useful for identifying servers with the least available memory.

## Histogram Query

Suppose your application exposes:

```text
http_request_duration_seconds_bucket
```

To calculate the 95th percentile response time:

```promql
histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
)
```

| `increase()` | Total increase over a period |
| `sum()` | Add values |
| `avg()` | Average |
| `max()` | Highest value |
| `min()` | Lowest value |
| `count()` | Count series |
| `topk()` | Top N values |
| `bottomk()` | Lowest N values |
| `histogram_quantile()` | Calculate histogram percentiles |

# PromQL — Interview Questions

### What is PromQL?

PromQL is the query language used to retrieve, filter, aggregate, and analyze metrics stored in Prometheus.

### What does the `up` metric represent?

The `up` metric indicates whether Prometheus can successfully scrape a target.

- `1` = Target is reachable and being scraped.
- `0` = Target is unreachable or the scrape failed.

### What is the difference between `rate()` and `increase()`?

`rate()` calculates the average per-second rate of increase for a counter over a time range.

Example:

```promql
rate(http_requests_total[5m])
```

Requests per second over the last 5 minutes.

`increase()` calculates the total increase of a counter over a time range.

Example:

```promql
increase(http_requests_total[5m])
```

Total requests during the last 5 minutes.

### Why should rate() be used with Counters?

Counters only increase over time, except when they reset after a restart. `rate()` correctly calculates how quickly the counter is increasing and automatically handles counter resets.

# Alert Lifecycle

An alert goes through several states.

```text
Normal
  ↓
Pending
  ↓
Firing
  ↓
Resolved
```

### Normal

Everything is healthy.

```text
CPU = 30%
No alert
```

### Pending

Condition becomes true, but the `for` duration has not completed.

```text
CPU = 90%
for: 5m
```

### Firing

Condition stays true for the required duration.

Alertmanager sends a notification.

### Resolved

Problem is fixed.

```text
CPU = 30%
```

Alert is automatically resolved.

# Alerting — Interview Questions

### What is Alerting in Prometheus?

Alerting is the process of automatically detecting abnormal conditions using PromQL expressions and notifying users through Alertmanager.

### Does Prometheus send emails directly?

No. Prometheus evaluates alert rules and sends alerts to Alertmanager.

Alertmanager is responsible for sending notifications through email, Slack, Microsoft Teams, PagerDuty, webhooks, and more.

### What is the purpose of the `for` field?

The `for` field specifies how long a condition must remain true before an alert fires. It helps avoid false alerts caused by temporary spikes.

### Labels vs Annotations

| Labels | Annotations |
|---|---|
| Used for routing and grouping alerts | Used to provide descriptive information |
| Machine-readable metadata | Human-readable messages |
| Example: `severity: critical` | Example: `summary: CPU usage is above 80%` |

### What is the alert lifecycle?

1. **Normal** – condition is false.
2. **Pending** – condition is true but hasn’t met the `for` duration.
3. **Firing** – condition has remained true for the duration, and Alertmanager is notified.
4. **Resolved** – condition returns to normal.

# Prometheus Storage

Prometheus uses a built-in database called TSDB (Time Series Database) to store metrics.

### Simple Definition

Prometheus storage is the mechanism by which Prometheus stores time-stamped metrics in its local TSDB.

> Time Series Data = Data + Timestamp

By default, data is stored at:

```text
/data
```

## Docker

```bash
docker run -v prometheus-data:/prometheus prom/prometheus
```

## Kubernetes

Usually attached to a PVC.

Check the storage path:

```bash
ps -ef | grep prometheus
```

# TSDB Structure

Inside the storage directory:

```text
data/
├── chunks_head   → Recent metrics
├── wal           → Write Ahead Log
├── lock          → Prevent multiple access
└── 01KXXXXXXX    → Block IDs / Historical data
```

# Write Ahead Log (WAL)

Before writing metrics permanently, Prometheus writes them to `wal/`.

This protects against crashes.

Flow:

```text
Metric Arrives
    ↓
Write to WAL
    ↓
Write to TSDB
    ↓
Delete Old WAL Entries
```

## Why WAL?

Suppose:

```text
CPU = 90%
```

Prometheus receives the metric.

Suddenly the server crashes.

Without WAL:

> Metric Lost

With WAL:

> Prometheus can recover the metric from the WAL.

# Blocks

Prometheus stores historical data in blocks.

Examples:

```text
01ABC
01DEF
01XYZ
```

Each block contains:

- Metrics
- Index
- Metadata

Example structure:

```text
01ABC/
├── chunks
├── index
└── meta.json
```

# Retention Period

Prometheus does not store metrics forever.

Default retention:

```text
15 days
```

We can change it.

Example:

```bash
--storage.tsdb.retention.time=30d
```

# Retention by Size

We can also limit storage size.

Example:

```bash
--storage.tsdb.retention.size=50GB
```

Meaning:

> Keep data until storage reaches 50 GB.

```text
Exporter
    ↓
Prometheus
    ↓

    ↓
Memory
    ↓
TSDB Blocks
    ↓

```

# Storage — Interview Questions

### Where does Prometheus store metrics?

Prometheus stores metrics in its built-in Time Series Database (TSDB).

### What is TSDB?

TSDB (Time Series Database) is Prometheus’s internal database designed to store time-stamped metrics efficiently.

### What is WAL?

WAL (Write Ahead Log) temporarily stores metrics before they are written to TSDB blocks, helping Prometheus recover data after crashes.

### What is the default retention period?

```text
15 days
```

### Why is Prometheus not suitable for long-term storage?

Prometheus uses local storage and is optimized for short to medium retention periods.

For multi-year storage and high availability, tools like:

- Thanos
- Cortex
- Mimir

are typically used.

### How do you persist Prometheus data in Kubernetes?

By using a Persistent Volume (PV) and Persistent Volume Claim (PVC) attached to the Prometheus Pod.
